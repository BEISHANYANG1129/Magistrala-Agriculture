# 智能农业机器人实施计划（零硬件版）

> 更新日期：2026-09-23  
> 当前条件：没有机器人实体，也没有主控板、传感器、电机、水泵等任何硬件。  
> 目标：先在普通电脑上完成可运行、可演示、可测试的“模拟机器人＋控制服务＋网页”。文中的移动、测量、浇水均为**软件模拟**，不代表真实机器人已通过安全验证。

## 一、第一版做成什么样

第一版演示应能按以下顺序走完：

1. 用户在网页选择一条含 3～5 个巡检点的固定路线，启动任务。
2. 模拟机器人依次“到达”各点，生成带设备、点位和时间戳的空气温度、空气湿度、土壤湿度数据。
3. 当某点土壤湿度低于阈值，控制服务检查模拟水位、电量、传感器有效性、浇水上限和间隔，决定是否发出一次限时浇水命令。
4. 模拟机器人返回“已收到、执行中、已完成”或明确的失败原因；网页显示进度、传感器数据、模拟浇水记录和故障。
5. 演示者可以注入障碍、断网、低电量、缺水、传感器故障、重复命令等情况，看到暂停、拒绝、失败或恢复后的结果。

首版范围是**固定路线、点位采样、规则浇水、故障模拟、网页监控**。真实行驶、真实测量、真实出水、自动绕障、自动返航和 LLM 自主控制均不属于零硬件验收范围。停车距离、续航、出水量误差和田间可靠性只能在将来取得硬件后实测。

## 二、当前项目起点

| 模块 | 仓库现状 | 零硬件阶段的处理 |
| --- | --- | --- |
| agriControlService | 可接收任务并规划动作；任务在内存队列中；执行器只打印命令并写日志 | 接入模拟器，补齐任务状态、设备回执、幂等和持久化 |
| magistrala-ui | 已有登录、设备、频道和农业集成页面 | 增加明确标为“模拟”的机器人演示页 |
| agriDataIntegration / agriDeviceExecutor | 主要对接第三方农业平台 | 演示不依赖它们，也不向真实第三方设备发送命令 |
| llm | 可形成控制意图 | 作为可选的建议入口，不阻塞首版闭环 |
| magistrala | 本地为子模块指针，但缺少 .gitmodules URL，目录为空；详见 README_LOCAL.md | 模拟闭环先独立运行；取得可复现的核心部署后再接入 |

仓库已有未提交修改。开始开发前记录 Git 状态，在现有工作上增量修改，不覆盖已有页面与配置。过期令牌和第三方凭据不能作为模拟演示的启动条件，也不要写入新示例文件。

## 三、排期和共用规则

- **排期参考**：一位熟悉 Go 与 Vue 的开发者约 4～6 周。按验收结果推进；遇到依赖缺失时，先完成不依赖该环境的工作。
- **所需条件**：一台开发电脑、Go、Node.js、项目依赖和浏览器。已有 run-local.ps1 与 README_LOCAL.md 可作本地启动参考；无需购买器件。
- **场景可复现**：先用固定场景文件，不用随机传感器值。输入相同场景应得到相同的事件顺序与业务结果。
- **结果以模拟器回执为准**：任务入队、命令发出、模拟器确认和动作完成是四件不同的事，接口与页面必须分别表示。
- **数据注明来源**：任务、遥测、事件和网页均标记 simulation，防止未来与真机数据混淆。
- **无需等待平台核心**：在 Magistrala 核心缺席时，使用本地持久化完成模拟闭环；平台接入是条件具备后的独立阶段。

## 四、分阶段执行

### 阶段 0：固定演示范围和环境（第 1～3 天）

**具体步骤**

1. 写一份最小演示场景：1 台虚拟机器人、1 条固定路线、3～5 个编号点位。每点准备一组固定读数；至少一处低于浇水阈值、一处高于阈值。
2. 为场景设置模拟电量、水位、土壤湿度阈值、单次最长浇水时长和两次浇水最短间隔。注明这些只是软件规则，不是真实设备规格。
3. 画出“网页建任务 → 控制服务校验 → 模拟器执行 → 回执和遥测保存 → 网页查询”的流程，并列出每步失败时该显示什么。
4. 按 README_LOCAL.md 核对 Go、Node.js 和 npm 依赖，尝试独立启动 control 与 ui；记录命令、端口和报错。不连接第三方真实农业平台。
5. 确定本地数据目录和配置格式，准备不含密钥的示例配置。

**交付物**：零硬件演示场景文档、场景数据文件、环境启动记录。  
**验收方法**：另一位开发者只看文档就能复述正常巡检的预期步骤，并可启动现有控制服务和前端。Magistrala 核心未就绪时明确记录，不阻塞下一阶段。

### 阶段 1：协议与模拟机器人（第 4～8 天）

**具体步骤**

1. 写机器人模拟协议，定义任务、命令、回执、遥测和故障事件的 JSON 格式及单位。至少包含 device_id、task_id、command_id、point_id、timestamp、mode、status、error_code；命令有有效期，传感器值可标记无效。
2. 实现简单状态机：空闲、巡检、采样、模拟浇水、暂停、故障。写清每个状态允许哪些命令。
3. 按场景文件顺序模拟“出发、到点、采样、规则判断、浇水、结束”，每次变化都输出事件与时间戳。
4. 增加可切换的障碍、离线、低电量、缺水、传感器无效、命令超时。障碍或离线时暂停移动；缺水、低电量或读数无效时拒绝浇水。
5. 同一 command_id 再次收到时返回先前结果，不重复浇水；过期命令明确拒绝。

**交付物**：模拟器、示例场景、协议文档、启动说明。  
**验收方法**：命令行可跑完正常巡检；切换每种故障能得到可预测状态和错误码；重复命令只产生一次浇水记录。

### 阶段 2：控制服务闭环（第 2～3 周）

**具体步骤**

1. 给控制服务增加模拟器适配器，把规划动作转为模拟器命令；执行器“打印成功”不能作为设备成功。
2. 修正 POST /control/task 的返回含义：返回“已接收/已入队”和任务 ID。当前返回的 task executed 与异步入队行为不一致。
3. 增加任务查询与状态流转：accepted、queued、sent、acknowledged、running、completed、failed、cancelled。保存状态时间、命令 ID、错误原因和最终结果。
4. 将任务、命令和回执保存到本地。服务重启后历史可查；未完成任务按照写明的规则恢复或失败，不能静默显示完成。
5. 浇水前用确定性规则检查：读数有效且低于阈值、水位和电量足够、设备在线、单次时长未超限、浇水间隔满足要求。
6. 处理超时、重复提交、取消和断线。LLM 若参与，只能提交与人工相同格式的建议或任务，走同一套校验。

**交付物**：模拟器适配器、任务状态 API、本地持久化、核心行为测试。  
**验收方法**：一项浇水任务可追踪到具体命令、模拟器确认与完成回执；重启后仍可查询；重复提交、过期命令和断网不会造成第二次浇水。

### 阶段 3：网页演示（第 3～4 周）

**具体步骤**

1. 在 magistrala-ui 增加“模拟机器人”入口，页眉持续显示“模拟环境 / 无实体设备”。
2. 总览显示在线状态、模式、当前点位、电量、水位、模拟泵状态、障碍状态和最后更新时间。
3. 任务区提供选路线、开始、暂停、继续、取消；显示任务 ID、时间线、点位进度和每条命令的回执。
4. 数据区按点位显示空气温度、空气湿度、土壤湿度历史，注明单位、采样时间与无效读数。
5. 故障区提供预设故障切换，显示注入时间、影响、恢复操作和最终结果。浇水记录只显示模拟运行时长及触发原因，不声称真实出水量。
6. 增加加载、失败、离线、空数据提示；刷新后从后端重新读取任务和历史，不能只靠前端内存。

**交付物**：模拟机器人页面、操作说明、演示脚本。  
**验收方法**：只用网页即可完成一次正常巡检和一次障碍或缺水演示；页面不会把“命令已发送”写成“执行完成”。

### 阶段 4：平台接入（第 4～5 周，条件具备时开展）

**开始条件**：取得可复现的 Magistrala 核心来源或确定的测试部署地址、版本和认证方式。缺少这些条件时保留本地模拟闭环，直接做阶段 5；不要为演示接入真实第三方控制设备。

**具体步骤**

1. 给模拟机器人建立独立设备身份，将遥测和故障事件上传到平台测试环境。
2. 统一设备 ID、点位 ID、时间戳和单位，记录控制服务、本地存储和平台的字段映射。
3. 对照本地与平台记录，处理重复、乱序和断线补传；平台不可用时任务仍有明确状态，本地历史仍可查询。
4. 在网页验证按设备和点位查询历史，保留模拟来源标记，记录测试数据的建立和清理方法。

**交付物**：平台适配器、部署说明、字段映射表。  
**验收方法**：一次模拟巡检的数据能在平台和网页按同一设备、同一点位查到；恢复连接后没有重复展示或丢失最终任务结果。

### 阶段 5：自动检查与交付（第 5～6 周）

**具体步骤**

1. 为状态流转、浇水规则、命令幂等和重启恢复编写自动测试，检查业务结果而不只检查函数是否被调用。
2. 固定验收场景：正常巡检、阈值以下浇水、阈值以上不浇水、缺水拒绝、低电量拒绝、障碍暂停、断网恢复、重复命令、过期命令、服务重启。
3. 运行相关前后端构建与测试，记录命令、结果和失败项。故障演示通过场景切换完成，不靠临时改代码。
4. 请未参与开发的人按说明独立启动一次，修订其遇到的步骤问题。
5. 保存演示日志、关键截图和已知问题，明确哪些结论只适用于模拟环境。

**交付物**：测试记录、可重复演示脚本、启动说明、已知问题清单。  
**验收方法**：完整流程可连续重复演示；每个异常场景有可解释的最终状态；新开发者能按文档启动并完成演示。

## 五、里程碑

| 里程碑 | 目标时间 | 展示结果 | 进入下一步的条件 |
| --- | --- | --- | --- |
| M0 演示规格 | 第 1 周前半 | 固定路线、样例数据、流程图、启动记录 | 每种模拟行为有预期结果 |
| M1 模拟器 | 第 2 周初 | 命令行巡检及故障注入 | 状态、回执和遥测格式稳定 |
| M2 控制闭环 | 第 3 周末 | 任务 → 命令 → 回执 → 历史查询 | 重复命令与重启测试通过 |
| M3 网页演示 | 第 4 周末 | 网页正常巡检及故障演示 | 用户能看懂当前状态与最终结果 |
| M4 可复现交付 | 第 6 周末 | 按文档启动、运行验收场景 | 独立人员能重复演示 |

M4 不依赖 Magistrala 核心接入；平台环境提前就绪时可同时完成阶段 4。若现有代码与新协议差异较大，可调整日期，但保持各里程碑的验收内容。

## 六、最终验收清单

- [ ] 页面显著标注“模拟机器人”，遥测带来源、设备、点位和时间。
- [ ] 一条 3～5 点路线可以启动、暂停、继续、取消并查询结果。
- [ ] 阈值以下且条件满足时模拟浇水一次；阈值以上不浇水。
- [ ] 缺水、低电量、传感器无效及过期命令被拒绝，并有明确原因。
- [ ] 障碍导致暂停；断网与恢复时状态准确。
- [ ] 同一命令重复发送不会重复浇水。
- [ ] 已发送、已确认、执行中、完成或失败可以分别查询。
- [ ] 服务重启或网页刷新后，任务及历史仍可查。
- [ ] 演示与测试可复现，不需要任何硬件或第三方真实设备。

## 七、将来取得硬件后

零硬件阶段只预留通信适配器和协议，不预先确定主控板、底盘、传感器或水泵型号。取得硬件后，先补场地、供电、接线、土壤采样方式和浇水计量方案，再用真实设备适配器替换模拟器，并另做台架与场地测试。急停、断网停机、缺水停泵、障碍停车距离、测量误差和连续运行都必须实测；模拟测试通过不能替代这些结果。
