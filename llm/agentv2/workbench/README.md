# 农业智能工作台

默认推理模型：`qwen3.5:9b`。复用已有 Go 服务的工作区鉴权、调用者 Reader 凭据与单任务运行锁；不建立另一套平台设备、分组、位置或围栏。旧区域分析前端源码归档在 `../web/legacy-platform-workbench.vue`，新页面位于 `magistrala-ui/src/components/AgentWorkbench.vue`。

## 启动

在 `D:\personal\magistrala\main\Magistrala` 运行：

```powershell
powershell -ExecutionPolicy Bypass -File .\run-local.ps1 agent-ui
```

服务使用新端口 `127.0.0.1:9026`、独立状态目录 `llm/agentv2/runtime/intelligent-workbench/`。前端现有 `/api/agent` 代理改指向该端口。旧 9025 服务及其区域配置不迁移、不覆盖。前端运行 `run-local.ps1 ui`，进入工作区的“智能工作台”。

启动首次将原有日志重新解析为 `weather-replay.json`；不调用模型、不下载模型、不修改原始文件或平台资源。更新日志后可显式重新导入，并重启本服务：

```powershell
python .\llm\agentv2\scripts\import_workbench_data.py --root D:\personal\magistrala --output .\llm\agentv2\runtime\intelligent-workbench\weather-replay.json
```

`AGRI_WORKBENCH_PREVIEW=1` 关闭推理，保留数据查询与检索预览；`AGRI_WORKBENCH_MODEL` 可显式覆盖模型。旧的 `AGRI_UI_MODEL` 仍仅用于兼容旧分析引擎，不影响新工作台的默认模型。推理前沿用 GPU 空闲检查，不停止或卸载其他任务的模型。

Ollama 调用参数集中在 `model.go`，每次调用后释放本次模型。环境和图片角色调用各自设置超时，自动化后台任务上限十五分钟。分析与复核超时后，报告步骤根据已有证据决定能发布什么。

## 本次实现

- **自动化任务**：用户提交一次自然语言目标和可选资料。`automation_understanding.go` 先识别任务类型，再分别提取设备、观测、照片参数，`automation_planner.go` 组装并核对结构化 `GoalPlan`，记录环境与图片的独立指令、来源要求、时间、依赖，以及设备的原始称呼、动作、时长、请求模式和触发要求。任务分类不再使用关键词、固定句式或正则路由。程序校验字段和依赖图，另一模型调用复核任务含义；不通过时携带具体失败原因和候选计划修正一次，仍失败则返回可重试的 `planner_failed`，不归咎于目标不明确。
- **意图与暂停**：独立言语意图复核只读取原话和补充答复，区分委托执行、方法咨询、只读任务和意图不明，不接受候选计划作为判断依据。读取消息、查数据、看已存照片不进入执行器操作。模型的自由文本不直接决定是否暂停；程序根据具体缺失参数、能力契约、未表示的多动作请求与前置步骤状态生成补充问题。计划保存协议版本，旧版计划在恢复时重新核对。
- **资料与编排**：资料查找器消费计划字段，不重新匹配用户句式。观测使用登记气象站及有效窗口，照片使用同工作区既有叶片分析原图，或 `-workbench-photo-sources` 登记的只读相机消息。来源ID、工作区、日期与时长仍由工具按契约核对。没有核实地块映射或时间时提出具体问题。独立分支先完成，有依赖的分支等待前一步。页面显示理解的任务、实际资料和缺口，支持自然语言补充并沿用同一条任务；已完成报告保留。
- **时间锚点**：自动化用独立的 Microsoft Recognizers-Text 实例检查原话是否包含可解析的时间锚点，不改动问答助手的时间组件状态。无锚点时，结构化输出不能生成日期窗口；明确查询全部已导入记录则由资料工具读取实际覆盖范围。组件结果可能分段识别，窗口语义仍与用户原文核对，不能把工具识别的片段无声替换成完整请求。手工附上的有效时段始终可用。原始任务、补充答复和已完成分支保留在同一条记录中。
- **执行模式**：`automation_capabilities.go` 登记实际执行工具及其功能契约，由能力匹配角色选择功能相符的工具，再由程序核对登记ID。理解操作要求与检查执行能力分开。未明确要求模拟的设备指令保留 `real` 请求模式。当前未接通真实设备映射、控制与回读接口，系统说明这一缺口；可模拟的水流开关任务显示“改为模拟”，用户选择后用通用虚拟阀门准备草案，原始目标和真实请求仍保存。该选择不触发执行，管理员仍须确认具体草案版本。模拟请求可自然描述动作与时长，中文数字及时间单位由模型归一化。当前单次模拟支持开启1–300秒后关闭或立即关闭，不将水泵等设备替换成阀门。
- **自动化边界**：首版由用户手动发起。条件、预约、重复、多个设备动作，以及操作后重新采集的流程，保留其原始要求并解释对应能力缺口；不能删掉这些要求后假装完成。服务重启会把未结束的自动化标记为中断，可人工继续分析；模拟状态未知时不重放。模型输出不授予设备权限，不运行模型生成的代码。
- **问答**采用连续对话界面。服务根据当前工作区内的 `parent_id` 恢复当前分支，按预算带入问答原文及必要的历史摘要。现场数值需要附上本轮的数据窗口。问答流即时传递检索、生成和复核进度。用户可停止生成或从历史打开对话。
- **检索**：首版为中文双字词和英文词项的词法 RAG，不是向量检索。工程资料分段保存来源、正文、适用范围、内容版本，按工作区、作物与整理状态筛选。目前八条项目工程说明；没有把演示知识或未审核农艺资料作为真实决策依据。可通过现有接口替换为向量/混合检索。
- **环境**：任务编排根据输入选择一个或两个同源窗口。取数节点保存各自的观测快照，质量诊断节点交付限制和准入统计，环境角色只收到准入数值。报告逐条保留通过核对的解释，并用程序统计补齐缺少的窗口简报。程序仍可独立提供只读统计。
- **图片**：接受来源明确的 PNG/JPEG，最大 2 MiB、最多两千万像素。原图登记和基础质量检查后，由可替换的视觉工具交付带图片指纹及工具版本的结构化发现。默认视觉工具调用 Qwen 看原图，解释角色接收结构化发现而不接收原图。图片过小、非叶片或质量不足时暂停专业解释并给出补拍提示。图像与本地气象关联、病虫害准确率和真实诊断仍需专项验证。
- **执行**：模拟草案可以引用同工作区的已保存环境分析快照，动作和时长由操作者选择。草案绑定能力版本、关闭步骤及有效期，确认绑定具体版本。模拟适配器分别处理受理和状态回读，保存虚拟时间内的开启/关闭变化；缺少关闭回读时记录为未知。重复确认已完成草案返回已有回执。真实控制继续以阀门接入和回读核查为前提。
- **复核**：环境与图片先检查每条候选陈述的数字、引用和证据类型，再由同一底模按索引给出通过、拒绝或无法判断。只有已通过的陈述进入报告，固定格式的观测简报可由程序独立生成。问答助手继续使用其原有复核流程。

自动化使用模型生成、程序核对的受限任务依赖图；环境和图片内部仍有各自的取证、质量、专业分析和报告步骤。持久化解释后的计划、补充答复、规划修正原因、节点结果、证据快照指纹、质量结论、视觉工具输出和逐项复核结果。已知质量诊断和执行约束由程序承担，任务理解、专业分析与语义复核使用不同的模型调用和输入契约。执行按草案、人工确认、适配器调用与回读推进。

## API

所有路径前缀为 `/v2/workbench`，平台集成模式要求当前登录用户 Bearer 令牌和 `X-Workspace-ID`。查询与模型分析只要求工作区访问权限；生成和确认模拟草案要求工作区管理权限。历史记录按工作区隔离。调用不接受模型生成的身份或权限。

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/status` | 模型配置、能力、当前工作区可用历史范围；不是模型推理健康证明 |
| POST | `/query` | 明确来源与时间窗的观测统计，不调用模型 |
| POST | `/runs` | `qa`、`environment`、`image`任务；环境可带同来源、同设备的 `compare` 起止时间 |
| POST | `/chat` | `qa` 对话流，接受可选 `parent_id`，以 NDJSON 返回 `stage`、`thinking`、`claim`、`result` 或 `error` |
| GET | `/history` | 当前工作区任务和已保存回执，可用 `task` 筛选类型 |
| GET | `/conversations` | 当前工作区的问答对话列表，按最后一轮时间倒序 |
| GET | `/conversations/{id}` | 指定对话的所有已保存问答 |
| POST | `/automation` | 接受任务目标、可选观测范围和图片，返回任务 ID，后端继续运行 |
| GET | `/automation` / `/automation/{id}` | 本工作区自动化任务列表，或指定任务的进度、报告和草案 |
| POST | `/automation/{id}/resume` | 给待补充、中断或规划失败的任务增加资料并继续；`clarification` 接受自然语言答复，`execution_mode:"simulation"` 明确选择模拟 |
| POST | `/plans` | 固定模拟阀门草案，可用 `basis_run_id` 绑定同工作区分析 |
| POST | `/simulate` | `id + revision + confirm:true`，精确确认及幂等模拟 |

查询窗口采用开始含、结束不含，最大七天。平台 Reader 使用远端时间过滤、有限分页，并在本地再次过滤设备和时间；超过分页上限会失败，不返回冒充完整结果的统计。

问答流开启 Ollama 思考模式，`thinking.delta` 单独传输模型返回的思考片段。思考内容仅保留在当前对话页面，不参与证据复核，不保存到历史，也不作为追问上下文。

追问优先携带当前分支完整的已保存问答。后端按序列化后的 UTF-8 字节估算上下文用量，并预留本轮生成和复核空间。超出预算时压缩较旧问答并保留近期原文，后续可复用摘要。整理模型超时或不可用时使用限长的原文摘录。历史和摘要仅用于理解追问。本轮 RAG 优先检索新问题，回指之前资料时可重新加载当前工作区和作物可用、且版本一致的片段。

状态目录用本机文件保存问题、结果、证据、图片及对话摘要，供单个服务实例使用。保留全部已保存的对话，按上下轮关系把现有记录归为整段对话。自动化父任务关联环境、图片子报告和模拟回执，页面任务记录只列父任务。已有历史文件可直接加载，旧版保存的对话摘要仍可用于追问。

## 自动查询与时间解析

问答查询保存设备、指标、统计方式、时间窗口和来源等结构化条件，供同一对话分支继续使用。已完成的查询与待补条件均随历史持久化。「最低呢」「换成27号」「不是温度，是湿度」只修改对应条件；明确询问当前读数时重新查询最新记录。平台请求使用当前调用者的工作区和凭据。

集成模式使用本地 Microsoft Recognizers-Text 中文时间组件，依赖固定于 `time-recognizer/package-lock.json`。需要 Node.js，首次可在 agentv2 目录运行 `npm ci --prefix time-recognizer --ignore-scripts`。启动脚本发现缺失依赖时提示修复方式并继续启动服务。组件初始化或运行失败时，问答返回「时间解析组件不可用」，环境、图像和自动化入口继续使用各自流程。状态接口的 `time_recognizer_status` 展示组件状态；每次问答会重新尝试组件，依赖修复后可自动恢复。

平台以 Asia/Shanghai 解析时间，省略年份的月日采用当年，单独补充日号时继承已选月份。下午按12时至18时处理，明确的日期范围包含末日，再转为开始含、结束不含的时间窗口。后端检查未来时间、日期合法性和单次七天上限。项目内的规范时间转换继续用于已保存条件、时段政策和组件未识别的明确格式。

`qa_language_test.go` 验证自然表达、连续修改条件、多项统计、日期纠正和重启续接。安装组件后，`qa_time_component_test.go` 直接验证真实的中文时间组件。

## 验证与尚待完成

`go test -p 1 ./...` 覆盖数据窗口、准入、来源筛选、引用/数字错误、复核失败、跨工作区、精确确认、重复提交、重启恢复与图片输入。前端单元测试覆盖问答出处、人工确认及切换工作区后的异步响应隔离。

`magistrala-ui/scripts/workbench-smoke.mjs` 验证真实本地页面、平台查询和模拟链路；`--automation` 验证一次提交触发环境与图片两个分支，`--model` 增加真实问答，`--image` 使用已有室内 Go1 图片验证视觉接口。实测结果与截图保存于 `output/multi-agent-rebuild/implementation/`。

`magistrala-ui/scripts/workbench-semantic-planner-smoke.mjs` 联调实际 Qwen、当前工作区资源和页面，检查自然语言设备操作、中文时长和单位换算、否定和条件、真实能力缺口、显式转模拟、刷新续接与精确确认，以及中文时段取数和相机照片查找。结构化规划与能力边界单元测试在 `automation_planner_test.go`，不把注入的测试模型当成语言理解能力验证。

设计参考用户提供的 NeuralFSM（状态与协调）、VERIMAP（结构化交接、验证与失败反馈）和 DECOR（规划、过滤、综合分工），以及 [LangGraph workflows and agents](https://docs.langchain.com/oss/python/langgraph/workflows-agents)、[interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts) 与 [Anthropic building effective agents](https://www.anthropic.com/research/building-effective-agents)。这里采用其工程设计思路，没有训练论文的强化学习策略，也没有迁移到其他框架或模型服务。

后续需增加审核过的农业知识、叶片数据集与独立测试、多实例存储，以及核实真实阀门接入后再实施设备适配。
